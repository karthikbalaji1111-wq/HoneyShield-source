# Decoy (honey-token) deployment guide

Every decoy is generated by HoneyShield (`Projects & decoys` in the console, or
`POST /api/v1/projects/{domain}/honey-tokens/generate`). Values are never chosen by tenants.
Rotation issues a new value **and a new artifact** that you must redeploy; the old value keeps
recording triggers as evidence.

| Type | Artifact | Detected by | Default severity | False-positive sources |
|---|---|---|---|---|
| URL | `https://<ingest>/t/<value>` | HoneyShield (PUBLIC_INGEST) | HIGH | someone legitimately opening an internal page that contains it; security scanners crawling internal docs |
| LINK | hidden `<a href>` to the same kind of URL | HoneyShield | MEDIUM | crawlers, link previewers (Slack/Teams/Outlook unfurling), browser prefetch |
| PIXEL | `<img src=https://<ingest>/px/<value>.gif>` for decoy documents/emails | HoneyShield | HIGH | mail clients/proxies that pre-fetch images (Apple Mail Privacy Protection, Gmail proxy), document indexers |
| FORM_FIELD | empty off-screen `<input>` honeypot | your form handler via the hook (CUSTOMER_HOOK) | MEDIUM | password managers / browser autofill occasionally filling hidden fields |
| API_KEY | decoy credential (generic / Stripe-like / OpenAI-like format) | your auth middleware via the hook | CRITICAL | internal scanners or CI jobs that try every key they find |

## Placement

**URL** — internal wiki pages titled like admin consoles, `robots.txt` `Disallow:` lines,
commented-out config entries, decoy bookmarks in privileged workstations, fake "backup" links in
runbooks. Never on public pages that search engines index.

**LINK** — inside internal pages, hidden. Expect occasional crawler noise; triage by user agent.

**PIXEL** — only in decoy documents (`Passwords_2026.docx`, "Board deck – confidential") and decoy
emails in mailboxes attackers would read. **Never in normal web pages**: every visitor would
trigger it (the generator no longer emits a page snippet for that reason).

**FORM_FIELD** — paste `html_snippet` inside each protected form; do not pre-fill, require or
validate it client-side; check it server-side with `hook.check_form(...)`. Reject the submission
as you normally would for bots.

**API_KEY** — decoy `.env` files, CI variable dumps, old repository branches, internal docs.
Add `hook.check_api_key(...)` to your authentication middleware. Do **not** plant real keys, and
remember that use against third-party APIs cannot be detected.

## Triage of an event

1. **Source**: PUBLIC_INGEST (HoneyShield saw it), CUSTOMER_HOOK (your integration reported it;
   IP/time asserted by you), MANUAL (entered by a named user with a reason), LEGACY_UNVERIFIED.
2. **Severity** comes from the decoy type, never from the caller.
3. **IP** is the first untrusted hop as seen by HoneyShield's proxy (spoofed X-Forwarded-For is
   ignored). Check the threat timeline for the IP (`Overview → Top attackers`).
4. **User agent / path** are attacker-controlled; treat as indicators, not facts.
5. Repeats beyond 60/min per IP and decoy are summarised by a `DETECTION_HITS_SUPPRESSED` audit
   record instead of individual events.
